# PRD：具身数据领域对象

## 1. 直接结论

第二个实施包补齐 Dataset、Standard、CollectionMethod 和 PeerCompanyProfile 四类长期对象。Event 仍是唯一事实节点；领域对象只保存稳定属性和经来源约束的声明，并通过关系表引用 Event。

本包继续保持私有、可逆：不进入公开 DTO，不切换页面，不改写当前快照，不将 fixture 描述为已接入生产内容。

## 2. 用户与决策

首要用户是具身数据生产运营团队。本包支持四类决策：

1. 哪些数据集可用于路线比较、训练或验收？
2. 哪些正式标准、事实标准或项目格式值得采用？
3. 不同采集方法的设备、模态、质量、吞吐、成本和风险边界是什么？
4. 同行公司声称具备哪些能力，哪些声明已被独立证据验证？

## 3. 目标

- 为四类领域对象建立严格、版本化的 Zod Schema。
- 建立对象表、Event 关系表和 Actor 能力声明/证据关系。
- 提供 Repository 写入、读取、列表和关系维护契约。
- 扩展仓库快照，支持新对象和关系的确定性往返及旧快照兼容。
- 提供至少三个 Dataset、三个 Standard、三个 CollectionMethod 的真实公开 fixture。
- 明确区分公司已收录、自报能力、独立验证和冲突证据。

## 4. 非目标

- 不把 fixture 写入 seed、当前数据库或版本化快照。
- 不新增、启用或晋级 Source。
- 不建立公开数据资产页、同行矩阵或搜索筛选。
- 不批量关联现有 Event。
- 不清理通用 AI 数据。
- 不声明 MySQL 兼容。

## 5. 核心行为

### 5.1 Dataset

Dataset 保存名称、版本、发布方、公开链接、管线维度、规模声明、采集配置、质量方法、许可、访问方式、用途、结果与限制。每个数字声明必须包含公开来源 URL。

### 5.2 Standard

Standard 必须显式区分 `formal`、`de-facto` 和 `project-format`。对象保存组织、版本、状态、适用阶段、Schema/坐标/同步/元数据等范围、实现、采用与迁移要求。

### 5.3 CollectionMethod

CollectionMethod 保存适用场景、本体、任务、设备、角色、环境、模态、质量边界、吞吐、成本、复杂度、安全风险、优势、限制、失败模式和成熟度。

### 5.4 PeerCompanyProfile

PeerCompanyProfile 从现有 Actor 和多条能力声明聚合。每条声明独立保存原文、声明方、来源、时间、核验状态、置信度和限制，并可关联验证或冲突 Event。

## 6. 验收标准

- 四类合法对象可写入、读取、关联 Event 并通过快照往返。
- Schema 拒绝额外字段、非 HTTPS 来源、无来源的数字声明和非法枚举。
- 删除 Event 只删除关系，不删除长期对象；删除长期对象级联删除其关系。
- 删除 Actor 级联删除能力声明与证据关系。
- 旧快照缺少新字段时可恢复，且不会生成领域对象。
- fixture 只包含经官方项目、官方文档或原始论文核验的事实；不确定项使用空数组或 `null`，不得推断补齐。
- `npm run check` 与 `npm run build` 通过。
